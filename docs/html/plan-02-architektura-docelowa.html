02 — Architektura docelowa

Stan kodu opisany tutaj pochodzi z przeglądu repozytorium 2026-10-09 (odczyt kodu, bez budowania). Liczby o crate'ach: ../CATALOG.md. Obecna architektura: ../ARCHITECTURE.md.

Trzy pojęcia:

  • Host — proces z AppCore, modułami i Brokerem. Dziś żyje wewnątrz okna Tauri; docelowo może działać także bez okna (moduł host-headless).
  • Klient — interfejs Svelte. Ten sam kod w trzech opakowaniach: okno Tauri, strona WWW (PWA), aplikacja Android (Tauri mobile).
  • Transport — sposób przesłania poleceń i zdarzeń. Klient nie wie, którego używa.

Szew 1 — fabryka platform

Dziś. Porty są zdefiniowane czysto (ok. 30 w platform-contract, m.in. FsPort, ExecPort, ClipboardPort, HotkeyPort, TrayPort, SecurePipePort, UiaPort, ScreenCapturePort; poza nim AudioIo, SecretStore, KeyVault, ShellPort). AppOptions przyjmuje każdy port jako Option<Arc<dyn …>>. Ale korzeń kompozycji wpisuje typy Windows wprost w ok. 10 miejscach (app-core/src/parts/*, app-agents/src/sysnet.rs, app-gui, app-terminal, app-broker, app-safety).

Docelowo. Jeden moduł platform-select z funkcją platform() -> PlatformPorts, wybierający implementację przez cfg(target_os). Korzeń kompozycji zna tylko PlatformPorts. Port, którego system nie ma, zwraca Unsupported — a interfejs ukrywa zależną od niego funkcję na podstawie mapy zdolności hosta (niżej).

// szkic — źródłem prawdy będzie crate platform-contract
pub struct PlatformPorts {
    pub fs: Arc<dyn FsPort>,
    pub exec: Arc<dyn ExecPort>,
    pub secrets: Arc<dyn SecretStore>,
    pub audio: Option<Arc<dyn AudioIo>>,       // brak = głos niedostępny na tej platformie
    pub uia: Option<Arc<dyn UiaPort>>,         // brak = sterowanie komputerem niedostępne
    /* … pozostałe porty … */
    pub capabilities: HostCapabilities,        // co ten host potrafi — trafia do klientów
}

Szew 3 — protokół niezależny od transportu

Dziś. 227 poleceń w jednej liście (app-api/src/commands.rs, makro with_commands!), 40 zdarzeń (AlfaEvent w app-api/src/dto/events.rs), DTO w app-api/src/dto/. Interfejs zna tylko AlfaClient (apps/desktop/ui/src/lib/api/client.ts) — ma dwie implementacje: TauriAlfaClient i FakeAlfaClient. To bardzo dobry punkt wyjścia. Brakuje pięciu rzeczy:

BrakSkutek dziśRozwiązanie
Numery sekwencji zdarzeńklient, który nie nadąża, po cichu gubi paczki (pump.rs)każde zdarzenie dostaje seq; host trzyma bufor ostatnich N; klient po przerwie prosi „od seq”, a gdy bufor nie sięga — dostaje resync i czyta stan od nowa
Błędy strukturalne na łączupowłoka spłaszcza AppError do tekstuprzez łącze idzie { code, message, details }; tekst tłumaczy klient
Tożsamość klienta i uprawnieniajedyne ACL to uprawnienia okien Taurikażda sesja klienta ma ClientId, rodzaj (okno / urządzenie sparowane) i zestaw dozwolonych poleceń
Polecenia zakładające lokalną maszynęokna dialogowe systemu, podgląd asset:, ścieżki bezwzględne w DTOpolecenia oznaczone local_only; dla klientów zdalnych odpowiedniki: wybór pliku z listy hosta, podgląd przesyłany strumieniem
Typy TS pisane ręcznieryzyko rozjazdu przy trzech klientachgenerator z Rust (ADR 0013); CI sprawdza git diff --exit-code

Ramka protokołu (szkic do ADR 0019):

→ { "v": 1, "id": 4711, "cmd": "turn_send", "args": { … } }
← { "v": 1, "id": 4711, "ok": { … } }            albo  "err": { "code": "…", "message": "…" }
← { "v": 1, "seq": 90211, "events": [ { "type": "TurnDelta", … }, … ] }
→ { "v": 1, "id": 4712, "cmd": "events_resume", "args": { "after_seq": 90180 } }

Wersja protokołu v jest negocjowana przy połączeniu; host obsługuje bieżącą i poprzednią, żeby telefon z nieaktualną aplikacją nadal działał.

Szew 4 — host bez okna

AppCore::build(paths, options) już działa bez Tauri (shell: None, HeadlessShell), ale nie ma pliku wykonywalnego, który by go uruchomił. Moduł host-headless daje binarkę alfa-host: start przy logowaniu (opcjonalnie), ikona w zasobniku przez okno Tauri uruchamiane na żądanie, brama klientów zdalnych. Okno Tauri staje się wtedy jednym z klientów hosta — lokalnym, przez nazwany potok — zamiast jego właścicielem.

Przejście jest dwustopniowe, żeby nie ryzykować wersji Windows: najpierw brama klientów wewnątrz obecnego procesu aplikacji (zdalny dostęp działa, gdy Alfa jest uruchomiona), potem wydzielenie hosta.

Mapa gotowości kodu

Gotowe na wiele platform

  • Dyscyplina kontrakt / implementacja / atrapa i wstrzykiwanie portów przez AppOptions.
  • Rdzeń logiki — magistrala, rejestr, konfiguracja, sesje, wyszukiwanie, pamięć, transfer, router, dostawcy chmurowi, licznik kosztów, persony, harmonogram, wyzwalacze, środowisko agentek, klasyfikator ryzyka, środowisko wtyczek, lib-* — CI buduje i testuje go także na Ubuntu.
  • Jedna powierzchnia poleceń i zdarzeń; interfejs z pełną atrapą działa w zwykłej przeglądarce.
  • Format .alfa (ścieżki względne), katalog dostawców, zarządzanie procesami llama.cpp i whisper.cpp, lokalny kanał MCP (ma już gałąź dla gniazda Unix), ścieżki danych (AppPaths ma gałąź XDG).

Potrzebny szew

  • Fabryka platform, protokół zdalny (pięć braków wyżej), generator typów TS.
  • Magazyn sekretów i kluczy dla Linuksa i Androida.
  • Semantyka ścieżek, powłok i tożsamości w kontraktach Brokera.
  • Nowy rodzaj dowodu zgody (obszar pod przeglądem człowieka).
  • Wymiar system / architektura w katalogu silników i modeli (app-models/src/data.rs zna tylko Windows x64).
  • Zmienne środowiskowe wpisane na sztywno w binarkach Jądra, watchdoga i aktualizatora.
  • Układ interfejsu na szerokość telefonu (dziś minimum okna to 400 × 500 px).

Tylko Windows

  • Siedem crate'ów platform-windows-*-impl, voice-audio-impl (WASAPI) i z nim cały głos na żywo.
  • Jądro poza procesem: usługa, potoki z DACL, okno Brokera na podwyższonej integralności, dowód fizycznego wejścia, skrót watchdoga.
  • Launcher, aktualizator, instalator NSIS, proces wydania.
  • Narzędzia sterowania komputerem: okna, UIA, wejście, ekran, Office, rejestr, OCR, terminal.

Drobiazg znaleziony przy przeglądzie: crates/app-bridges/src/app.rs:227 wybiera cmd dla systemów innych niż Windows — do poprawienia w etapie B.
